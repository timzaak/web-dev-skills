# Acceptance Contract

所有 accept agent、独立 Demo 验收入口及任务编排在验收前读取。本协议是验收输入、结论、报告、只读边界与结果消费的唯一公共定义；领域 guide 只补充检查对象和证据，专项协议只补充领域门禁。行为验证、阶段承接和运行证据复用按 [验证证据协议](${CLAUDE_PLUGIN_ROOT}/protocols/verification-evidence-contract.md)。

## 输入与范围

- feature 或目标文件、当前 phase，以及适用的 slot/item。
- 本轮变更范围、设计与需求来源、上游 Handoff、实际命令和原始证据入口、验证责任表及上游待验证场景。
- 设计输入按 [core quality](${CLAUDE_PLUGIN_ROOT}/guides/core/quality.md) 判断适用性；需求和故事映射按 [需求来源协议](${CLAUDE_PLUGIN_ROOT}/protocols/requirement-source-contract.md)，不把任务命名前缀作为跳过检查的依据。

只检查当前范围及其依赖和回归风险。逐项确定必要门禁；不适用项记录原因，不为满足模板新增前端、API、设备或测试框架。缺少影响验收目标的上下文时，记录未验证并交回调用方裁决，不以假设放行。

## 门禁、问题与结论

门禁结果使用 `passed | failed | unverified | not_applicable`。`passed` 必须有可复核证据；`not_applicable` 必须有范围依据；必要门禁不能以“不适用”掩盖缺少环境、账号、设备、工具或运行结果。门禁表不能为空；全部不适用时交回调用方确认范围，不返回通过。

验收问题统一分级：

- P0：无法构建/运行、核心流程阻塞，或其他阻断交付的缺陷。
- P1：功能、公共契约、权限/安全边界或本轮验收目标受损。
- P2：不影响验收目标的维护性、结构或表达改进。复杂度、重复代码和类型写法本身不自动升级；发现具体行为风险时按影响定级。

| 结论 | 条件 | `task_completion.status` |
|---|---|---|
| `REJECTED` | 任一必要门禁失败/未验证，或存在未解决 P0/P1 | `failed` |
| `ACCEPTED_WITH_IMPROVEMENTS` | 必要门禁全部通过，仅有 P2 改进 | `success` |
| `ACCEPTED` | 必要门禁全部通过，无未解决问题 | `success` |

拒绝优先于其他结论。分数、重复率或平均覆盖率不能抵消必要门禁；本协议不要求评分。Demo 按本轮必要故事场景逐项核对关键断言和有效整文件执行证据，不能用已测场景占比豁免必要场景。后续阶段承接仅按验证证据协议放行，不把尚未执行的场景标记为通过；最终承接阶段不得留有待验证项。

## 只读边界与派生物

- 不编辑业务源码或测试，不修复断言，不读写任务 `.state.json`；状态和修复调度由调用方负责。
- 允许写 `.ai/quality/` 报告及附件，按项目真实命令产生日志、缓存、构建和测试派生物，并在隔离测试环境执行必要验证与清理。
- OpenAPI/API 客户端等受版本控制的生成物，仅在项目有明确生成命令、输出范围已知且本轮需要时允许生成；不手工编辑。执行前后核对差异，报告实际变化，重新验证受影响消费者；变化使上游证据失效时交回编排层按证据协议重开对应验证，不能继续沿用旧成功。
- 生成命令存在未知写入、自动修复源码或无法区分用户已有改动时，交回 dev 执行，不扩大写入范围或回滚用户改动。
- 重复代码检查优先复用有效证据；项目已有工具或变更存在明显复制风险时，限定受影响源码并排除生成物。无工具时可人工核查并说明依据，不自动安装工具，不以固定百分比替代缺陷判断。

## 报告与结构化返回

每轮写新报告：`.ai/quality/<agent-name>-<feature-or-target>-<YYYYMMDD-HHMMSS>[-unique].md`。目标名须能区分同名文件与共享 agent 的不同 phase；同秒重试追加唯一后缀，不覆盖旧报告。批量另写 `<agent-name>-summary-<YYYYMMDD-HHMMSS>[-unique].md`，引用所有单文件报告并统计结论。

批量有拒绝或验收未完成则批次拒绝；否则有改进项则带改进通过，其余通过。汇总返回同样的验收字段，`report_path` 指向汇总，按文件汇集门禁、问题及待承接场景，不漏掉派发失败。无目标时报告无可验收目标，不生成通过结论。

报告包含范围与来源、本轮结论、必要门禁及证据复用依据、P0/P1/P2 问题（位置、证据、影响和修复建议）、未验证场景及承接位置、派生物变化和清理结果。明确区分“本阶段通过”与“业务验收待完成”。

在 [agent output](${CLAUDE_PLUGIN_ROOT}/protocols/agent-task-output-contract.md) 的 `task_completion` 中增加以下必填字段，不用自然语言摘要代替：

- `acceptance_result`：上表结论。
- `report_path`：已成功写入且可读取的本轮报告路径。
- `gates`：本轮必要门禁列表；每项包含 `name`、`result`、`evidence`（证据路径数组）；失败/未验证/不适用时补 `reason`。
- `findings`：未解决问题数组；每项包含 `severity`、`location`、`evidence`（证据路径数组）、`impact`、`suggested_fix`。无问题时为空数组。
- `pending_verification`：后续承接数组；每项包含 `scenario`、`owner`、`location`。无承接时为空数组。

`change_scope` 只表示实际改动，不表示检查范围；只写报告/日志时九项为 false，受版本控制的生成物变化按实际层填写。执行了全部检查但发现缺陷时，仍按 `REJECTED/failed` 返回。报告写入失败、字段缺失或结论与门禁/问题不一致是无效验收输出；不得编造报告路径或将其视为通过。

## 调用方消费与恢复

调用方先确认报告存在、结构完整且结论与证据一致，不能仅凭 `status=success` 标记验收完成；有效的两个通过结论才允许完成当前验收。无效输出保留失败原因并重新取得有效报告，不由主会话代出或改写结论。

有效拒绝交回对应 dev/test 责任方，修复并重测后重新验收；环境或用户裁决缺口先解除条件，不空转派发。状态迁移、停止/重试策略由各入口协议决定，accept 不跨阶段编排。重入时先核对已有证据有效性，仅补缺失或失效验证，每次仍输出独立新报告；上次中断或旧成功不能替代本轮结论。
