# Security Review Contract

t-security-review 的漏洞识别指令、误报过滤指令、finding/裁定结构和报告结构的单一事实源。复刻来源见 `skills/t-security-review/SKILL.md` 的来源说明。

本契约只做安全审查并输出报告，不修复任何问题；代码质量清理属于 t-simplify，正确性缺陷复查属于 `/code-review` 与各阶段 accept。

## 漏洞识别指令集

识别 sub agent（`security-vuln-finder`）的 prompt 必须完整注入本节。

### 目标

对本次分支变更做聚焦安全审查，识别**高置信度、有真实利用潜力**的安全漏洞。这不是通用代码审查：只关注**本次变更新增**的安全影响，不评论仓库里既有代码的安全问题。

### 关键指令

1. 压低误报：只报告对实际可利用性有 >80% 把握的问题。
2. 避免噪音：跳过理论性问题、风格问题和低影响发现。
3. 聚焦影响：优先报告可导致未授权访问、数据泄露或系统沦陷的漏洞。
4. 排除项（不予报告）：
   - 拒绝服务（DOS）漏洞，即使允许中断服务。
   - 存储在磁盘上的密钥或敏感数据（由其他流程负责）。
   - 限流或资源耗尽问题。

### 安全类别清单

**输入校验漏洞：**
- 未净化用户输入导致的 SQL 注入
- 系统调用或子进程中的命令注入
- XML 解析中的 XXE 注入
- 模板引擎中的模板注入
- 数据库查询中的 NoSQL 注入
- 文件操作中的路径穿越

**认证与授权问题：**
- 认证绕过逻辑
- 提权路径
- 会话管理缺陷
- JWT token 漏洞
- 授权逻辑绕过

**加密与密钥管理：**
- 硬编码的 API key、密码或 token
- 弱加密算法或实现
- 不当的密钥存储或管理
- 密码学随机性问题
- 证书校验绕过

**注入与代码执行：**
- 反序列化导致的远程代码执行
- Python pickle 注入
- YAML 反序列化漏洞
- 动态代码执行中的 eval 注入
- Web 应用 XSS 漏洞（反射型、存储型、DOM 型）

**数据暴露：**
- 敏感数据写入日志或存储
- PII 处理违规
- API 端点数据泄露
- 调试信息暴露

补充：即使仅可从本地网络利用，仍可以是 HIGH 严重度问题。

### 分析方法

**Phase 1 — 仓库上下文调研（使用文件检索工具）：**
- 识别项目已使用的安全框架与库。
- 寻找代码库中已成型的安全编码模式。
- 检查既有的净化与校验模式。
- 理解项目的安全模型与威胁模型。

**Phase 2 — 对比分析：**
- 把新变更与既有安全模式对比。
- 识别对既有安全实践的偏离。
- 找出不一致的安全实现。
- 标记引入新攻击面的代码。

**Phase 3 — 漏洞评估：**
- 逐个检查修改文件的安全影响。
- 从用户输入追踪数据流到敏感操作。
- 找出不安全跨越权限边界的位置。
- 识别注入点和不安全反序列化。

### Finding 结构

每条发现按以下结构返回（对应原文的 markdown 输出格式）：

```text
- file:
  line:
  severity: HIGH|MEDIUM|LOW
  category:        # 如 sql_injection、xss、command_injection
  description:     # 漏洞机制，单段说明
  exploit_scenario: # 具体攻击场景：攻击者如何构造输入、达成什么后果
  recommendation:  # 修复建议
```

- `exploit_scenario` 必须具体到攻击路径；写不出攻击场景的发现不返回。
- 无发现时返回空列表并附一句范围确认说明。

### 严重度标准

- **HIGH**：可直接利用，导致 RCE、数据泄露或认证绕过。
- **MEDIUM**：需要特定条件才可利用，但影响显著。
- **LOW**：纵深防御问题或低影响漏洞。

### 置信度标准（识别阶段）

- 0.9–1.0：已确认利用路径，可能时已验证。
- 0.8–0.9：清晰的漏洞模式，有已知利用方法。
- 0.7–0.8：可疑模式，需要特定条件才可利用。
- 低于 0.7：不报告（过于投机）。

### 最终提醒

只关注 HIGH 和 MEDIUM 发现。宁可漏掉一些理论问题，也不要用误报淹没报告。每条发现都应是安全工程师在 PR review 中有把握直接提出的问题。

## 误报过滤指令集

误报过滤 sub agent（`security-fp-filter`）的 prompt 必须完整注入本节。过滤 agent 只读代码判定真伪，不需要运行命令复现漏洞；不使用 Bash、不写任何文件。

### 硬排除项

命中以下模式直接判定为误报：

1. DOS 漏洞或资源耗尽攻击。
2. 磁盘上存储的密钥或凭据（若本身已有其他防护）。
3. 限流或服务过载问题。
4. 内存占用或 CPU 耗尽问题。
5. 非安全关键字段缺少输入校验，且无法证明有安全影响。
6. GitHub Actions 工作流的输入净化问题，除非明确可由不受信输入触发。
7. 缺少加固措施。代码不需要实现全部安全最佳实践，只报告具体漏洞。
8. 理论性而非实际可行的竞态条件或时序攻击。只报告确有实际问题的竞态。
9. 过时的第三方库相关漏洞。它们由独立流程管理，不在此报告。
10. 内存安全问题（缓冲区溢出、use-after-free）在 Rust 等内存安全语言中不可能发生，不报告。
11. 仅为单元测试或测试运行使用的文件。
12. 日志伪造。把未净化的用户输入写日志不是漏洞。
13. 只能控制 path 的 SSRF。只有能控制 host 或协议时 SSRF 才算问题。
14. 把用户可控内容拼进 AI system prompt 不是漏洞。
15. 正则注入。把不受信内容注入正则不是漏洞。
16. Regex DOS 问题。
17. 不安全的文档。不报告 markdown 等文档文件中的任何发现。
18. 缺少审计日志不是漏洞。

### 判例（PRECEDENTS）

1. 明文记录高价值密钥是漏洞；记录 URL 默认视为安全。
2. UUID 可视为不可猜测，无需校验。
3. 环境变量和 CLI 参数是受信值。安全环境下攻击者通常无法修改它们；任何依赖控制环境变量的攻击无效。
4. 内存或文件描述符泄漏等资源管理问题无效。
5. tabnabbing、XS-Leaks、原型污染、开放重定向等细微或低影响的 Web 漏洞，除非极高置信度，不报告。
6. React 和 Angular 默认可防御 XSS。除非使用 `dangerouslySetInnerHTML`、`bypassSecurityTrustHtml` 或类似不安全方法，否则不报告 React/Angular 组件或 tsx 文件中的 XSS。
7. GitHub Actions 工作流中的多数漏洞实际不可利用。验证前必须确认有具体、明确的攻击路径。
8. 客户端 JS/TS 代码缺少权限校验或认证不是漏洞。客户端代码不受信，这些校验由服务端负责；所有把不受信数据发给后端的流程同理，后端负责校验和净化全部输入。
9. MEDIUM 发现只有在明显且具体时才保留。
10. ipython notebook（*.ipynb）中的多数漏洞实际不可利用。必须有不受信输入可触发的具体攻击路径才报告。
11. 记录非 PII 数据不是漏洞，即使数据可能敏感。只有日志暴露密钥、密码或 PII 等敏感信息时才报告。
12. shell 脚本中的命令注入通常实际不可利用，因为 shell 脚本一般不处理不受信输入。必须有不受信输入的具体攻击路径才报告。

### 信号质量标准

对未被硬排除的发现，逐项评估：

1. 是否存在具体、可利用、有清晰攻击路径的漏洞？
2. 这是真实安全风险，还是理论上的最佳实践？
3. 是否有具体代码位置和复现步骤？
4. 该发现对安全团队是否可执行？

### 裁定结构

对单条发现给出：

```text
finding: file:line | category 摘要
verdict: confirmed|false_positive|excluded
confidence: 1-10
reasoning:      # 引用硬排除项/判例编号或具体代码证据
```

置信度标尺：1–3 低置信度，很可能是误报或噪音；4–6 中置信度，需要调查；7–10 高置信度，很可能是真实漏洞。

## 聚合与置信度门槛

主流程聚合全部裁定后：

- `confidence < 8` 的发现一律丢弃，不进入报告。
- 同一漏洞被多条裁定覆盖时以最低置信度为准。
- 全部被过滤时不输出空报告凑数，报告结论写明"未发现高置信度安全问题"。

## Report

写入 `.ai/quality/security-review-[YYYYMMDD-HHMMSS].md`：

```text
# Security Review 报告 [YYYYMMDD-HHMMSS]

## 审查范围
- diff 基准: origin/HEAD...（或降级基准）
- 文件数 / 变更行数

## 确认的漏洞
### Vuln N: <category>: `<file>:<line>`
- Severity:
- Description:
- Exploit Scenario:
- Recommendation:

## 被过滤的发现
- file:line | category | 过滤原因（置信度不足 | 硬排除项 N | 判例 N）

## 结论
- 确认 N 项，过滤 M 项；或未发现高置信度安全问题
```

inline 降级模式（Agent tool 不可用）的报告必须在结论中声明：这是单主会话两遍审查，不是识别 + 并行过滤的多 agent 审查。
