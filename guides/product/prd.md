# 产品需求文档（PRD）编写规范

## 目标

本规范用于约束 `.ai/prd/**/*.md` 临时草稿和 `docs/prd/**/*.md` 正式 PRD 的内容边界，确保 PRD 聚焦“做什么/为什么做”，并与技术实现文档分层。用户故事的正式/候选来源边界参考 `${CLAUDE_PLUGIN_ROOT}/protocols/requirement-source-contract.md`。

每份 PRD 草稿或正式 PRD 必须同步具备 HTML Preview，用于人类快速审阅、反馈和迭代。

## 核心原则

- PRD 描述产品语义、业务边界、验收目标，不承载底层实现细节。
- 接口详细定义不在 PRD 中展开，PRD 只保留与产品语义相关的能力边界和约束。
- HTML Preview 是 PRD 的可视化审阅和协作视图，不替代 Markdown PRD，不引入新需求。
- 用户故事、PRD、HTML Preview、技术设计四类文档职责分离：
   - 用户故事：用户行为与价值
   - PRD：范围、规则、约束和验收目标
   - HTML Preview：目标能力的低保真可视化、关键流程、业务状态、已确认决策和审阅重点
   - 技术设计 / 接口文档：实现与接口细节
- 如需技术细节，使用 `/t-design` 单独产出。
- PRD 只保留当前有效的架构设计约束，不写过去时或历史变更说明。
- PRD 不记录当前任务是否已实现、完成比例、已完成/未完成清单等会随实现推进快速过期的进度状态。

## 明确禁止项

PRD 中禁止写入以下内容：

- 具体端点明细，如 `GET /api/...`、`POST /api/...`
- 请求参数表、响应字段表、状态码矩阵
- 数据库建表、迁移脚本、DDL、索引设计
- Java/TypeScript/SQL 结构体、接口或代码示例
- 足以替代技术设计或实现代码的技术细节
- 具体代码文件路径列表或文件索引
- 当前任务完成状态、实现进度、已完成/未完成清单

## API 章节规范

PRD 中 `API` 相关章节应包含：

- 接口能力范围，例如查询类、写入类、回调类
- 访问控制或数据边界原则，仅在需求明确涉及认证、角色或数据边界时描述
- 版本与兼容性原则
- 如有需要，可附接口文档或设计文档引用

PRD 中 `API` 相关章节禁止包含：

- 具体端点明细，如 `GET /api/...`
- 请求参数表、响应字段表
- HTTP 状态码逐条定义
- 可直接替代接口文档的 schema 细节

## 前端/交互章节规范

PRD 中前端相关章节可以包含：

- 页面入口和关键用户路径
- 关键交互、状态反馈、权限可见性
- 对业务语义有影响的展示约束

PRD 中前端相关章节禁止包含：

- 组件拆分方案
- 具体框架、库、Hook、表单 schema 设计
- 详细 API 调用代码或数据映射策略

## HTML Preview 规范

HTML Preview 路径：

- PRD 草稿: `.ai/prd/<domain>/<feature>.md`
- 正式 PRD: `docs/prd/<domain>/<feature>.md`
- Preview: `.ai/preview/<domain>/<feature>.html`

Preview 不进入代码仓库，由 `/t-html-show` 自动生成。

Preview 应结合“可视化 PRD 阅读器”和“低保真交互原型”，帮助人类快速理解：

- 这个功能解决什么问题
- PRD 定义的目标能力和目标体验是什么
- 做什么、不做什么
- 关键流程如何走
- 关键业务状态、异常和权限可见性是什么
- 哪些属于不改变产品语义的可视化假设或验证风险；需要用户裁决的产品问题必须在生成 Preview 前解决

有前端/交互入口时，Preview 的 UI 示意必须聚焦 PRD 定义的目标体验和关键状态，不复刻代码库已经具备的现有页面或组件。已有 UI 只能作为入口或约束说明出现。

Preview 不强制限定为单文件、内联 CSS/JS、无 npm/CDN/构建工具。为了提升可审阅性，可以使用外部样式、脚本、第三方图形库或辅助资源；如使用，必须在 Preview 可见区域声明依赖来源、用途和打开/运行方式，辅助资源必须写入 `.ai/preview/` 下，不得写入目标项目源码。

纯后端或无用户界面的功能仍需生成 Preview，但不生成伪 UI；应使用流程图、状态图、调用方场景、能力边界矩阵或验收矩阵表达。

`/t-prd` 生成或更新草稿 Preview 后，应立即打开 HTML 供人类审阅。后续沟通优先围绕 HTML Preview 进行；如果审阅中调整了功能意图、流程、状态或验收目标，必须同步修改 Markdown PRD 草稿、draft user story 和 HTML Preview。草稿通过 `/t-prd-check` 后进入 `/t-design`；如果草稿继续被修正，必须再次运行 `/t-prd-check`。实现、测试和 Demo 验收完成后，使用 `/t-prd-publish` 基于草稿、现有正式 PRD / 用户故事和实现后证据做发布总结，并修正 `docs/prd` / `docs/user-stories` 中缺失、过期或冲突的问题；完成后对应 `.ai/prd` 与 `.ai/user-stories` 草稿应删除。

## 与一致性检查的关系

PRD 一致性检查聚焦业务规则、访问控制语义、能力边界和验收目标，不要求 PRD 承担接口明细说明。

## 最低结构建议

PRD 至少应包含：

- 相关用户故事
- 范围界定（In / Out）
- 需求概述
- 业务规则与状态
- 功能需求
- API 相关约束（如适用）
- 前端/交互约束（如适用）
- 已确认决策
- 参考资料

对应 HTML Preview 至少应包含：

- Overview
- Scope
- Flow
- States
- Rules
- Acceptance
- Assumptions
