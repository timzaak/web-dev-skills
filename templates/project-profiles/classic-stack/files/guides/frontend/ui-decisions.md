# 前端 UI 决策规范

`t-design` 前端/扩展设计阶段的 UI 决策依据：组件选型、交互状态与反馈、无障碍底线、视觉纪律、复杂度准入。目标项目的组件体系、token 约定和设计语言优先于本页默认值；本页默认值只在目标项目没有明确约定时生效。

## 1. 复用阶梯

新建任何组件或依赖前按序判断：Inspect（查现有实现）→ Reuse（直接复用）→ Adapt（改内容/参数复用）→ Extend（扩展现有组件）→ Create（新建）。

- 新建组件必须写明前四级不可行的理由
- 现有依赖或原生能力（图标、工具函数、原生 API）能覆盖时不引入新依赖
- 用户只要求局部调整时保持最小 diff：不改公开 API，不重构无关部分

## 2. 组件选型

| 场景 | 默认选择 |
| --- | --- |
| 选项 4–10 个 | 原生 `<select>` |
| 选项超过 10 个或需要搜索 | combobox |
| 列表少于 100 条 | 普通列表，不虚拟化 |
| 平级视图切换 | tabs / segmented |
| 展示型内容折叠 | accordion |
| 异步时长不确定 | 骨架屏，超过 300ms 才显示 |
| 已知短操作 | 按钮内 loading |
| 可点击、可触发 | 语义元素（`<button>` / `<a>`），禁止 `<div onClick>` |

## 3. 交互状态与反馈

- 可交互组件覆盖 hover / focus / active / disabled / loading
- 数据视图覆盖加载 / 空态 / 错误 / 权限受限
- 反馈时机：100ms 内给出即时反馈；300ms 显示加载指示；超过 3s 说明进度或提供取消
- 空态可行动：告诉用户下一步能做什么，不只放说明或插画
- 错误态提供恢复路径：重试、修改输入或返回

## 4. 无障碍底线

以下为不可协商底线，不因范围压缩或进度压力省略：

- 所有操作可键盘完成：Tab 到达、Enter/Space 触发
- 图标按钮有可访问名（aria-label 或可见文本）
- 表单控件与 label 关联；placeholder 不充当 label
- 颜色不是唯一信息载体，错误、状态变更同时有文本或图标
- 触控目标不小于 44px

## 5. 视觉纪律

- 克制用色：大面积灰阶，强调色只留给最重要的动作和信息；处处强调等于没有强调
- 一切尺寸有出处：字号、间距、圆角、高度从项目现有 token 或工具类取值，不随手填数
- 用户的视觉语言先转译为设计策略再动手："高级"优先靠 typography、spacing 和层级，不是毛玻璃、渐变、发光全上；"简洁"不是删说明文案、全灰、icon-only 或全收进汉堡菜单
- z-index 使用项目现有档位管理，不随手写大数字

## 6. 复杂度准入与删除测试

装饰性效果（glass、glow、particles、3D 等）启用前过三问：

1. 是否服务当前任务？
2. 是否降低了其他复杂度？
3. 删掉它是否损害可用性、无障碍或信息层级？

三个答案都是"否"就删除。交付前对每个新增元素做删除测试：移除后不损害可用性即删除。
