# T-Tools 的泛化：结构流程与领域知识

T-Tools 的泛化依赖两层分离：结构流程负责可靠推进，领域知识来自真实项目、由人确认。当前 general 分支移除生产技术栈预设，仅保留通用 implementation 与可选 web-demo；Figma 同样保留。新的知识沉淀能力仍是[方案设计](generalization-plan.md)，不代表已经实现。

## 结构流程层

阶段编排、目标级或 phase/slot/item 执行闭环、磁盘状态恢复、证据失效重开、质量链与独立只读 accept 都不依赖项目语言。

判断一条规则的归属，可以把项目替换成数据管道、CLI 或其它交付形态：规则仍成立，通常属于结构；必须随语言、框架或团队偏好变化，则属于领域。

| 规则 | 归属 |
| --- | --- |
| 同一失败连续三次无进展转 blocked | 结构 |
| accept 独立只读并给出可复核证据 | 结构 |
| 新增测试资产时是否插入 test 角色 | 结构 |
| 用哪种测试框架与具体命令 | 领域 |
| 模块边界、架构与团队工程偏好 | 领域 |

历史上的 t-super-run-all 是结构组件可以独立增删的例子：它编排阶段、恢复游标与质量链，不需要承担具体领域实现。显式逐阶段还是无人值守连跑，属于结构流程的风险取舍，不应在每个新领域重新设计。

## 领域知识层

领域知识包括模块组织、角色实践、测试策略、验证入口与证据形态。它不能从项目名称、一个目录或模型偏好推导成既定规则，应先读项目 AGENTS.md、代码、配置、真实脚本与已确认文档。

同类项目可能有多套都成立的方案。候选应内部一致，给出代价、适用条件与对门禁的影响，再由人选择。已确认的决定复用，不重复提问；仍需裁决的缺口必须暴露，不能写入正式规范后继续执行。

## 当前落点

- skills 继续编排，通用 project-design/dev/test/accept 角色承担单一职责。
- 设计根据真实项目模块生成，不再固定列举生产交付端。
- implementation 承接开发与测试；有真实 Web 故事交付时才启用 web-demo。
- 项目 CI、环境与测试命令来自项目本地入口，插件不提供应用环境默认值。
- Web Demo 与 Figma 的专用实践保留；它们仍读取项目事实，不规定生产框架。

阶段、状态和输出契约在 protocols 中集中维护，不能用移除领域知识为由取消恢复与验收门禁。旧领域状态保留、重新规划，不静默映射为完成。

## 可选既有模板

移出的生产领域资产保留在 [templates/](/templates/index.md)，包括原领域集合与 java 分支的后端模板。它们按固定来源导出独立运行时，用户显式选择，通用主链路不自动加载。持续同步见[合并 main 指南](/human/merge-main.md)。

## 后续沉淀路径

先提取项目事实，形成有证据的候选；由用户确认选择；将最小规则发布到项目自己的知识基线；交付后从实际失败与验证中提出增量，并在来源漂移时重新检查。跨项目经验只作为待确认候选，不默认回写插件。

产物布局、确认门禁、发布恢复、失效处理、入口衔接与验收用例详见[领域知识沉淀方案](generalization-plan.md)。
