# Skill 测试与迭代

按风险选测试深度：新建或结构性大改走完整循环；微调只做写作准则自检和链接检查。形式校验（frontmatter、命名、死链）不能证明 skill 的决策质量，行为验证才能。

## 前向行为测试

1. 写 2-3 个真实用户会说的测试 prompt：带路径、上下文和口语细节的多步骤请求，不是抽象指令。先给用户过目："这几个用例对吗，要补充吗？"
2. 每个用例起一个独立 subagent 执行，只提供 skill 路径、任务 prompt 和必要输入文件；不给预期答案、不提示怀疑的缺陷或拟定的修复。执行者知道的越少，测试越接近真实用户。
3. 对照运行，确认变化来自 skill 本身：
   - 新建 skill：同 prompt 再跑一组不带 skill 的对照。
   - 更新 skill：先用 `cp -r` 快照旧版，对照运行新旧版本。
4. 测试在隔离的临时目录里进行，产物不进仓库主链路，测完清理。
5. 评估可观察的行为和产物：做了什么、漏了什么、是否越界。不检查措辞、标题个数或正则命中——那类断言测不出决策质量。

## 触发边界测试

针对 `description`（触发机制见 [skill 写作准则](${CLAUDE_PLUGIN_ROOT}/skills/t-skill/references/skill-writing-guide.md)）：

- 生成约 20 个查询并让用户过目：
  - 8-10 个 should-trigger：同一意图的不同说法（正式与口语）、用户没点名 skill 但明确需要它的场景、与相邻 skill 竞争但本 skill 应胜出的场景。
  - 8-10 个 near-miss should-not-trigger：共享关键词或领域但目标不同的查询——naive 关键词匹配会误触发的那种。
- 负例要真难。"写个 fibonacci 函数"对 PDF skill 这类一眼无关的查询不构成测试。
- 查询要具体真实：文件路径、列名、公司名、错别字、随口语气，而不是"处理这个文件"。
- 触发不理想时只改 description，不动正文；改完对失败用例重测。

## 迭代准则

- **从反馈泛化，不过拟合。** 某个用例反复失败时，优先换思路、换表述、换工作模式；堆更多 MUST 压住单个样例通常换来在别的请求上变差。
- **保持精简。** 每轮删掉不起作用的内容。若各次测试运行都在重复写同一个 helper 脚本，把它沉淀进 `scripts/` 并在 skill 中声明使用。
- **窄修正优于普遍规则。** 针对观察到的失败做最小修改；"以后所有情况都……"是给单次事故过度立法。
- **停下的信号。** 用户认可、反馈全部为空、或连续一轮没有实质改进。此时停止迭代，收尾验证后交付。
