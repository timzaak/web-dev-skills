# 从实际项目沉淀领域知识：方案设计

状态：提案。本文设计后续能力，尚未新增知识沉淀命令、注册表或自动发布机制。当前 general 分支先完成领域预设移除，保留通用 implementation、Web Demo、Figma 与现有质量/恢复契约。

## 1. 目标与边界

让项目实践随实际交付积累，后续 agent 可以找到、理解、验证并复用；既不反复从零摸索，也不把某个项目的偶然写法变成插件的普遍最佳实践。

结构流程继续由插件维护；技术领域知识首先属于目标项目。项目无需先建设知识库才能执行普通任务：已有 AGENTS.md、代码、配置与明确用户指令仍可直接支撑设计和执行。只有工作依赖一个尚未裁决的知识选择，或显式要求发布知识时，才触发相应确认门禁。可选 check 不变为主链路强制前置，accept 保持实现后的独立收口。

## 2. 资产分层与规则归属

| 层 | 建议位置 | 内容 | 消费条件 |
| --- | --- | --- | --- |
| 项目事实快照 | `.ai/knowledge/<topic>/evidence.md` | 实际目录、依赖版本、脚本、CI、代表实现与验证记录 | 调研可读；只证明观察到的事实 |
| 候选实践 | `.ai/knowledge/<topic>/proposal.md` | 替代方案、证据、代价、待裁决项和拟发布差异 | 只用于讨论，不作为 dev/test/accept 约束 |
| 生成状态 | `.ai/knowledge/<topic>/.state.json` | 当前步骤、来源指纹、候选版本、决策引用、失败与恢复位置 | 仅由知识 skill 推进 |
| 决策记录 | 当前 feature 的 `.ai/decision-log/<feature>.md` | 沿用 DEC/Q 机制保存用户选择与取代关系 | 发布前依据 Active Decision，正式文档内化结论与理由 |
| 已确认项目规则 | `docs/engineering/index.md`、`docs/engineering/<topic>.md` | 适用范围、必要规则、真实命令导航、证据和维护条件 | 已发布且未失效，才可作为工程约束 |
| 确定性操作 | 项目 `scripts/` | 已验证且确有重复执行需求的操作 | 真实入口、项目内维护 |
| 可移植经验包 | 独立、按需安装的领域包 | 脱离业务数据的候选经验与适用条件 | 在新项目重新比对并确认后启用 |

职责仍按仓库 AGENTS.md：skill 编排和写入；agent 单角色执行或只读校验；共享字段、状态、门禁将集中定义在新的知识协议；工程知识只写项目文档；重复执行操作才写脚本。本文只是设计，不充当现有运行时契约。

AGENTS.md 只保留 docs/engineering/index.md 的读取入口。命令执行说明继续在 scripts/index.md 单点维护，工程文档引用其条目，不再复制命令表。插件安装目录不写入项目经验，内部资源仍使用 `${CLAUDE_PLUGIN_ROOT}`。

## 3. 提取：先识别事实，再提出选择

首次接入或用户主动发起知识整理时：

1. 按当前 topic 窄范围读取项目 AGENTS.md、依赖清单/锁文件、CI、真实脚本和代表实现。记录路径、内容指纹、版本与观察上下文，不扫描并导入全部仓库知识。
2. 选取能代表目标能力的已有成功实现、必要的失败案例与实际验证证据。一个文件的写法只能标为“局部观察”，不能证明团队共识。
3. 将内容分为已有明确约束、可证明的事实、未确认偏好和未知缺口。已有用户决策直接引用；冲突实践并列展示并给出处，不能自行混合。
4. 对确实影响实施的选择给出 2–4 套内部一致的候选：模块边界、依赖组织、测试分工、验证门禁、证据形态成套说明，写清收益、成本、迁移影响与适用条件。简单的既有事实无需凑出多套方案。
5. 展示拟发布规则的逐项差异、覆盖范围、现有规则冲突和失败处理，再由用户裁决。明确的既有授权可复用，不重复询问；“按项目最佳实践”不能自动解释为批准某套新偏好。

用户未回答的选择保留在 proposal 和 Q 中，禁止写入已发布 docs、AGENTS.md 或角色规范；不阻塞与该选择无关的任务。单纯整理事实也不能静默提升为强制工程门禁。

## 4. 发布：以可审阅增量形成项目基线

建议新增单一职责入口 t-knowledge（名称为提案），只负责提取、确认和物化知识，不实现业务功能、不运行完整交付链、不替代技术预研。

建议支持“提案、发布、从磁盘恢复”三个显式动作。发布动作只有在用户已选择具体候选、来源仍有效、拟发布差异已展示、必要验证已完成时才能执行。先生成可审阅产物，最后确认具体差异；已获同一范围授权时不重复请求。

发布流程：

- 按已有决策连续性协议在当前 feature 账本记录选择与被替代规则；发布时把结论、理由和确认范围内化到正式工程文档，不依赖临时 DEC/Q。
- 把确认后的最小规则写入 docs/engineering/<topic>.md，更新索引；不改业务实现、不改插件共享 phase 或默认角色。
- 每条规则记录稳定 ID、适用路径/版本/条件、规则正文、理由、来源证据摘要、确认依据、验证入口引用和失效条件。明确“必须、建议、示例”的约束强度；无增量价值的知识不发布。
- 暂态 DEC/Q 与正式稳定规则 ID 的对应保存在本轮发布清单；正式规则不引用会被清理的 .ai 决策账本。证据摘要保留来源路径、版本/内容指纹与验证结论，日志路径作为辅助证据，清理日志本身不删除规则依据。
- 核对索引、引用与真实入口；发布清单记录旧/新内容指纹、备份、目标与已完成步骤；临时文件全部准备成功后逐项替换，索引最后更新。失败保留旧基线并记录失败步骤，恢复前核对用户修改，不凭状态字符串推定成功。单个发布批次只在全部目标文件一致时标记完成。

通用角色从项目索引按当前模块路由到适用规则，不默认加载整个知识库。项目已有规范目录时复用并记录路径映射，不再建设第二套相同规则。

## 5. 交付后的增量学习

知识线索来自真实工作：accept 拒绝、诊断确认的根因、同类回归、命令失效、被验证的工程取舍。每条候选至少包含触发条件、失败事实、根因证据、修复与验证、适用边界及反例。

accept 和诊断角色只提出候选并引用证据；由知识 skill 去重、关联现有规则并生成差异。不能让 accept 一边判失败一边修改验收标准，也不能让每次交付自动增加规范。

是否沉淀取决于复用价值与证据充分性，不以出现次数机械决定。单次高影响失败可提出规则，多次失败也可能只是同一未修复问题。复核后的规则应能改变后续决策，并有可执行或可观察的验证方式；纯经验感想留在报告。

## 6. 状态、恢复与失效

后续共享协议需集中定义：draft -> awaiting-decision -> confirmed -> publishing -> published。工具或写入失败进入 failed，保存失败步骤与最后有效产物；再次同一命令读取磁盘、核对来源后从未满足条件继续，不重复确认已有效的决定。

- 重复提取：按 topic + 来源指纹 + 规则 ID 去重，只写变化部分。
- 发布前来源变化：回到 draft，展示差异；只重新确认受影响的偏好，保留无关决策。
- 发布中断：先核对正式文件、临时文件与发布清单，一致则补记成功，否则完成同一批次或恢复旧基线；不盲目覆盖用户编辑。
- 已发布规则依赖的配置/版本/命令发生变化：标 stale，说明影响范围。消费者不能继续将失效规则当约束；可用现有项目事实完成的无关工作继续，涉及未决选择则交用户裁决。
- 冲突规则：沿用决策账本的取代关系，保留原因和来源；不叠加互相矛盾的“最佳实践”。
- 新规范改变当前计划或证据适用性：按现有验证协议重新打开受影响工作及 accept，不能让新规范自动证明旧交付通过。

需要检查来源内容指纹，不能只检查文件是否存在。CI 与环境仍由项目真实入口定义；知识中“存在该命令”和“该命令本轮运行通过”必须区分。

## 7. 与现有入口的衔接

| 入口 | 后续衔接方式 |
| --- | --- |
| t-init | 探测项目已有规范和真实运行入口，建立导航；不自动选架构，不静默生成领域规范 |
| t-decision / t-tech-research | 暴露领域路线与关键未知项，给候选提供证据；产品语义变化仍回 PRD |
| t-design | 按项目模块加载已确认适用规则，记录所用规则 ID/版本与未决缺口 |
| t-task / t-super-run | 计划只保存本轮所需规则路径与版本，不复制全文，不动态改插件协议 |
| project-dev / project-test | 按职责消费规则；新观察返回候选，不改正式知识 |
| project-accept / t-dream | 独立发现规范与实现漂移，产出可复核证据和沉淀线索 |
| t-review / t-simplify / t-push | 保持质量链；规则或脚本变化使证据失效时重验，项目 CI 缺失不当通过 |

当前只需要 implementation 与可选 web-demo，不为每门语言注册新 phase。未来只有项目确有独立交付/恢复边界时才讨论项目 phase 描述文件；届时须集中设计 phase 注册、顺序、角色、状态校验、消费者和兼容策略，不能只放开字符串而绕过共享契约。

Web Demo 和 Figma 继续由插件提供，但目标 URL、身份、项目模块与验证命令来自目标项目；不得借其入口重新引入生产技术栈默认规则。

## 8. 跨项目复用

先证明一条规则在来源项目有价值，再抽出通用部分，保留适用版本、前置条件、反例和项目差异点。可移植包只提供候选，默认不激活；新项目先对照自己的配置、代表实现和团队选择，再决定采用、改写或拒绝。

本分支已有 [classic-stack 与 Java 后端模板](/templates/index.md)，保留既有领域经验并可导出完整配套运行时；这是显式选择的历史模板来源，不代表自动识别、沉淀或发布新项目知识已经实现。模板与通用运行时分开维护，持续同步按[合并指南](/human/merge-main.md)。

首次实现不建设全局知识市场、自动评分推荐或自动发布回插件。只支持项目内闭环，待真实项目反馈后再判断独立领域包的维护成本与收益。

## 9. 实施拆分与验收

| 交付批次 | 范围 | 验收依据 |
| --- | --- | --- |
| 本次 general 分支 | 移除生产领域预设、通用角色/阶段、保留 Web Demo/Figma、同步说明 | 引用无断链；设计门禁、项目 hook、CI 失败/恢复和 Demo 脚本验证 |
| 后续项目内试点 | 新知识协议、t-knowledge 最小入口、项目规范导航 | 在一个实际项目完成事实 -> 候选 -> 用户选择 -> 发布 -> 角色消费 |
| 后续真实反馈迭代 | 交付后候选、去重、失效检测与恢复脚本 | 重复运行无重复规则；来源漂移重审；中断不破坏基线；accept 独立 |
| 有复用证据后 | 可移植领域包 | 第二个不同项目能选择性采用，且无需改结构流程 |

必测行为：现有规范可直接复用；多种实践并存需要裁决；缺命令或零用例不能发布为已验证；未回答不写正式规则；失败发布保留旧基线；来源变化不沿用失效确认；相同输入重复执行不重复写；规则变化触发相关证据重验；非 Web 项目不生成 Demo；Web Demo/Figma 仍可按实际项目运行。

本方案的完成标准是形成可维护的项目知识基线，并证明后续角色能按需使用；知识文件数量不作为成功指标。
