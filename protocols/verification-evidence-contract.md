# Verification Evidence Contract

供设计、任务规划、dev/test、accept 和执行收尾共同消费；同一会话已加载且未变化时复用，不重复全文读取。测试层级选择按 `${CLAUDE_PLUGIN_ROOT}/protocols/task-phase-execution.md`；本协议只定义验证责任、证据和完成门禁。

## 验证责任

- 改变业务规则、接口行为、权限、状态转换或用户操作流程时，必须规划受影响行为的运行验证；编译、类型检查、构建和静态审查不能单独证明行为正确。
- 优先复用真实场景测试、Demo 或项目现有集成验证。没有自动化入口时，可采用可复核的开发者工具、设备或人工验证，不为满足格式新建测试框架。
- 纯文档、类型整理、机械重构或样式变更按实际风险选择验证；静态验证足够时记录依据。样式变化需视觉核对、重构影响运行契约时，仍记录相应行为证据。
- 在设计测试章节、阶段 index 或 super-run phase 计划中记录一份最小验证表，item 的 Validation/Handoff 引用对应行；不新增运行时目录或状态文件：

| 场景/验收目标 | 入口与关键断言 | 承接 phase/item 或角色 | 结果与证据 |
|---|---|---|---|
| 受影响的可观察行为 | 真实命令或可复现步骤、预期业务结果 | 当前执行者或已声明的后续阶段 | 未执行 / 通过 / 失败 / 不适用及依据；证据路径 |

不涉及行为验证的任务可用一句适用性说明代替表格；不要求为未改变且无回归风险的路径补用例。

## 阶段交接与交付

- 当前阶段负责的必要验证全部通过，才允许 accept 通过。缺设备、环境、账号、工具或人工结果时记录未验证，交回编排层；不能以测试计划、截图占位或构建通过代替结果。
- 跨端业务场景可以明确交给后续 Demo/集成验证：设计和 active phases 中须有真实承接阶段，阶段 index/计划写明场景、入口、关键断言及承接位置。尚未生成下游 item 时至少定位到 phase 和设计章节，生成时补齐 item 引用。
- 上游 accept 可在本阶段必要门禁通过后放行，但报告与调用方收尾必须分别写明“本阶段通过”和“业务验收待完成”，列出未验证场景及后续阶段；不能把该场景标为通过。
- 后续阶段读取并关闭承接的验证行。最后一个承接阶段 accept 及 feature 交付收尾必须核对全部必要场景已有有效证据；存在遗漏、失败或无人承接的场景时拒绝验收，不以所有代码 item 完成推断业务完成。
- 不要求执行入口自动跨 phase。用户仅请求一个 phase 时照常停止并报告待完成验证；`.state.json` 的 phase 完成只表示阶段完成，沿用现有状态枚举。
- 下游验证失败由编排层按根因交回实现或测试角色；修复后重新执行受影响验证并重新验收。已有通过证据的失效处理见下节。

## 证据记录与复用

dev/test 在首次验证时记录，accept 独立核查；只写入现有 Handoff、运行报告或质量报告，不复制整段日志：

- 实际命令、工作目录、过滤范围或人工步骤，预期与实际结果；自动化记录退出码、执行的用例及失败/跳过情况，零用例或跳过必要场景不能算通过。
- 原始日志/报告/截图入口和采集者；截图应能对应具体步骤与结果，单张页面截图不能证明完整事务或数据持久化。
- 被验证代码、测试、fixture、依赖锁、配置和相关迁移的版本依据。已提交版本可用 commit；存在未提交/未跟踪文件时需相应内容指纹或运行前后可核对的快照，单凭相同 HEAD 或文件名列表不足以复用。
- 相关运行环境、构建产物、设备/profile、数据准备与清理结果。只记录能影响当前结论的条件，不收集无关环境信息或凭据。

accept 中的“执行验证”默认指取得并核查有效执行证据；已有证据满足以下条件时可复用，无需重跑命令：

1. 来源可读且结果可复核，覆盖本次全部必要断言和执行范围；不能只接受上游的“已通过”摘要。
2. 相关输入与实际加载产物未变，环境/数据条件仍适用；无关文件变动不自动使证据失效。
3. 无新失败、相互矛盾的证据、状态污染或不稳定迹象；项目门禁或用户没有明确要求独立重跑。

任一条件不满足时，补跑最小受影响验证并记录原因；无法确认影响范围或明确门禁要求时才升级。修复后的必要回归、Demo 整文件终验和现场证据要求继续适用；定向用例通过不能替代整文件门禁。

每次 accept 仍产出独立报告，注明复用的 run ID/证据位置与适用性核查，独立审查需求、断言质量和遗漏风险。复用运行证据不等于沿用旧验收结论。中断恢复先核对证据有效性，再执行缺失项；不盲目重复有副作用的操作。
