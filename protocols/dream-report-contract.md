# Dream Report Contract

## Modes

| 模式 | 写入边界 | 覆盖范围 |
| --- | --- | --- |
| `audit` | 只写 `.ai/quality/dream-check-[YYYYMMDD-HHMMSS].md` | 上下文治理、结构组织、traceability、关键描述/实现一致性抽样 |
| `govern-prd` | 可改 `docs/prd/**`、PRD 索引和必要引用；不得改实现代码 | audit + PRD 合并、归档、重写和引用修正 |
| `deep` | 只写 dream 报告 | audit + 后端模块级深度一致性 |
| `backend-only` | 只写 dream 报告 | PRD 与后端实现一致性；不覆盖上下文治理、结构组织、前端、Demo |

`--all` 默认先做索引级健康扫描；只有 `--all --deep` 或高风险模块才进入深挖。

## Candidate Issue

所有参与评分的问题必须使用以下字段：

```text
候选问题:
  - 标题:
    严重级别: P0|P1|P2|P3
    置信度: 0-100
    描述位置:
    实现证据:
    判断依据:
    修复方向: 修正文档|修正实现|整理文档结构|调整代码结构|调整测试结构|产品确认
    可能误报原因:
```

专项 agent 可以增加 `权威上下文地图`、`结构地图`、`整理计划`、`模块评分` 等字段，但不得省略候选问题字段。

最终 P0/P1 必须经过验证，且置信度不低于 80。低于 80 的发现只能进入“未能确认 / 观察项”，除非主线程二次验证后提高置信度。

## 提取类别与差异分级

### 描述声明提取

从 PRD、用户故事和 Demo 测试中提取可核验声明，只记录可被文件证据验证的：

- 能力边界：功能做什么、不做什么、角色能执行哪些操作。
- 数据与状态：关键实体、状态、字段约束、唯一性和生命周期。
- 验证规则：必填、长度、格式、边界条件和失败条件。
- 权限与租户边界：角色、权限、realm / tenant 隔离、跨租户访问限制。
- 业务流程：核心步骤、状态流转、错误处理和关键分支。
- 验收描述：用户故事 GWT、Demo 测试映射、关键断言和验收标准。

### 实现事实定位

按目标项目真实结构定位实现，不假定固定目录；若采用常见 Rust + Axum 布局，可优先检查：

- Domain：`backend/**/src/**/[module]*/`、实体、服务、策略和领域规则。
- HTTP/API：路由注册、handler、DTO、validator、OpenAPI 注解。
- Infrastructure：repository、外部集成、持久化约束和事务边界。
- Frontend：页面、组件、路由、查询/变更、权限可见性。
- Demo：`demo/e2e/**/*.e2e.ts` 或 `patrol_test/**/*_test.dart` 中的场景、注释、断言和日志。

后端模块检查的输入规则：

- 必须能在 `docs/prd/**/*.md` 中定位与 `[module]` 对应的 PRD。
- 目标仓库中与 `[module]` 对应的后端领域实现目录必须能被定位；若未采用固定布局，基于仓库真实结构搜索模块代码。
- HTTP/接口实现目录若不存在，记录为信息项，不直接判失败。

### 差异分级

逐项判断每个描述声明是否准确：

- PRD 声明的能力边界、权限规则或业务规则在代码中缺失 → P0。
- PRD 与代码在关键校验、权限、租户隔离或业务流程上冲突 → P0。
- PRD / 用户故事 / Demo 描述承诺了尚未实现或测试未覆盖的行为 → P0 或 P1，按影响定级。
- 代码已扩展新能力但 PRD 未更新语义说明 → P1。
- 用户故事或 Demo 描述与 PRD 不一致，但未发现实现冲突 → P1。
- 接口说明、路由名、字段名、示例数据或非关键说明失真 → P2；作为描述准确性问题单独记录。

每条差异必须判断优先修正文档还是实现：

- 文档错：实现事实合理，但 PRD / 故事 / Demo 描述失真。
- 实现错：PRD 描述合理且处于有效需求范围，但代码未实现或实现冲突。
- 需确认：缺少证据或存在产品决策空白。

## Scoring

默认 `audit` 总分 100：

- 上下文治理健康度：25
- 结构组织合理性：20
- Traceability 完整性：20
- 关键描述与实现事实一致性：25
- 证据链完整性：10

`deep` 总分 100：

- 上下文治理健康度：20
- 结构组织合理性：15
- Traceability 完整性：15
- 基础描述与实现事实一致性：25
- 后端深度一致性：25

后端深度一致性内部权重：

- API 能力边界：30%
- 数据模型一致性：25%
- 验证规则一致性：20%
- 权限一致性：15%
- 业务逻辑一致性：10%

`backend-only` 只计算 PRD 与后端实现一致性，并在报告中标注未覆盖范围。

默认 audit 的实现一致性分只对已抽样核验的关键声明负责；报告必须列出抽样范围和未覆盖范围。

## Report

`.ai/quality/dream-check-[YYYYMMDD-HHMMSS].md` 必须包含：

- 执行摘要、范围、模式和总分。
- 审计模式说明：`audit` / `govern-prd` / `backend-only` / `deep`，以及 `--all` 是否只做索引级扫描。
- 当前权威上下文地图。
- 上下文治理问题。
- 结构组织问题。
- Traceability 断链、错链、重复链和缺失证据。
- 被核验的描述声明清单。
- 实现一致性抽样范围、未覆盖范围和高风险模块选择依据。
- 分项得分、扣分原因和可复算公式。
- P0 / P1 / P2 / P3 差异列表。
- 未能确认 / 低置信度观察项。
- 每条差异的文档位置、实现证据、判断依据、置信度和修复方向。
- 深度模式下的模块评分表。
- subagent 执行矩阵：维度、状态、范围、问题数量、是否参与总分。
- 下一步修复建议。

## PRD Governance Output

`govern-prd` 最终答复必须包含：

- 新权威 PRD 列表。
- 归档或删除的旧 PRD 列表。
- 合并 / 归档 / 删除映射表。
- 主要规则收敛点。
- 验证命令和结果。
- 未处理风险或需要产品确认的问题。
