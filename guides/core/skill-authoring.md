# Skill 写作准则

融合 Anthropic skill-creator 与 Codex skill-creator 的写作实践。目标仓库（t-tools 插件仓库或目标项目）的硬性规则以其 AGENTS.md 为准；本文件只补充其之外的写作方法，冲突时以该 AGENTS.md 为准。skill 根目录的解析由调用方入口（`t-skill` 的模式）决定，不在本文件重复。

## 触发：description 是第一道门

模型只凭 name 和 description 决定是否加载 skill，正文只有触发后才进上下文。因此：

- 一句"做什么" + 具体触发场景（用户实际会怎么表述）+ 与相邻 skill 的消歧边界，三样都要有。
- 欠触发比过触发更常见。描述要主动覆盖用户可能的间接说法——"用户提到 X、Y、Z 时使用，即使没有明说 W"，而不是等用户点名命令。
- 主动不等于贪多：catchall 式的能力清单会吸引无关请求；排除项只写防误路由所需，不枚举全部不适用场景。
- 简单一步任务模型自己就能完成，不依赖 skill；评估触发质量时不要拿这类查询当用例，要用带上下文、多步骤的真实请求。

## 渐进披露：三级加载

1. name + description — 恒在上下文，保持简短且可辨别
2. SKILL.md 正文 — 触发即加载，目标 500 行以内，接近就分层
3. references / scripts — 按需读取或执行，不占常驻上下文

分层规则：

- 正文保留共享目标、必要约束、核心流程和路由（何时读哪个文件）；分场景流程、schema、大段示例进 references。
- 超过 300 行的 reference 在开头加目录或可检索关键词。
- 同一内容只在一处维护，正文与 references 不互相复制。
- 简单自足的 skill 不需要 references 和路由层；不要为了"结构完整"而加层。

## 结构：按需最小化

```text
<skill 根目录>/<name>/
|-- SKILL.md        必需：frontmatter + 正文
`-- references/     仅当正文放不下且内容按场景分头使用
```

skill 目录之外的归位按目标仓库区分：

- t-tools 插件仓库：需要落到仓库其他位置的，按其 AGENTS.md「规则归属」路由到 `agents/`、`protocols/`、`guides/`、`scripts/`，不在 skill 目录里复制一份。
- 目标项目：没有这套分层，规则默认收敛在 skill 目录内（SKILL.md + `references/` + 按需 `scripts/`）；项目 AGENTS.md 另有归位约定时从其约定。

不放入 skill 目录的东西：README、安装说明、changelog、正文的速查副本、没有调用方的占位文件。判断标准是"这个文件是否直接支撑 skill 的某次执行"；答案是否定的就不建。

## 内容取舍

逐条问：同样的请求、模型和工具条件下，省略这条内容会让哪个决策或结果变差？保留能解释具体后果的指导。用户授权与范围是执行约束，始终按实际授权处理。

- **领域决策规则。** 明确适用条件、应作的判断和可观察的验收证据。涉及多个调用方的契约引用其唯一维护位置。单次失败可提炼成回归用例，扩展成持久规则前先核实适用范围。
- **运行态产物。** 错误描述、日志、任务拆分和验收报告沿用工作流的产物位置。在 skill 中只写证据位置、读取时机及判定所需字段。本轮运行 ID、通过数和日志原文仅留在原产物，正文、模板和示例统一使用占位符或另造最少的示例数据。依据下游消费、失败恢复和审计约定决定留存与清理。
- **执行约束。** 明确前置依赖、执行中必须始终成立的条件和完成标准。顺序影响正确性、权限、兼容性或恢复时，写明依赖与失败后果。其余路径由模型探测环境后选择。涉及阶段产物时写明来源、位置、成功条件及消费方。涉及持久状态时写明状态转换、恢复点、重跑行为和继续责任。
- **工具输入与输出。** 先用已有脚本或工具检索、转换和过滤证据。摘要应保留判定所需字段、失败详情及可追溯的原始路径。只有重复或必须确定性执行的操作才沉淀为脚本。需要 MCP 等外部能力时，说明触发条件、依赖以及来源不可用时如何继续或暂停。

交付前用本轮证据核对写入的正文、模板和引用文档。发现本轮运行 ID、计数或原始日志被写入时，改成来源路径或占位符并复查。演示决策时可直接写「输入：目标回归失败。输出：保留待评审状态，定位失败记录并在修复后重跑」。

例如，从一次验收记录提炼「发票去重」skill 时，把本轮通过日志和失败详情留在运行目录。经领域规则确认后，写入「同一账单只允许生成一张发票，验收时并发提交两次同一账单的开票请求，核对持久化结果只产生一张发票」。如果恢复依赖原失败记录，写明先定位该记录，修复后重跑受影响用例，再按既有门禁推进评审。

## 示例模式

固定输出格式用模板并声明强制：

```markdown
## 报告结构
必须使用以下模板：
# [标题]
## 摘要
## 发现
## 建议
```

约定类规则用 Input/Output 对，比抽象描述更可靠：

```markdown
## Commit message 格式
输入：Added user authentication with JWT tokens
输出：feat(auth): implement JWT-based authentication
```

## 更新既有 skill

- 保留原 `name` 与目录名；入口形式变化会破坏用户习惯和下游引用。
- 修改前先搜索引用它的 skill、protocol、guide、agent、README 和入口路由（插件仓库为 t-how 场景路由表）；删除内容前先看它的调用方和存在原因。
- 只改用户要求或行为验证暴露的问题，不顺手重构无关段落。
