# T-Tools 的泛化：结构流程与领域知识

T-Tools 当前内置的研发领域是 Web、Chrome 扩展、小程序、Flutter、用户故事 Demo 和 Figma 这一族。要让它适配其它类型的研发任务——数据工程、机器学习、CLI 工具、游戏、嵌入式——不需要重写工作流，只需要先回答一个问题：这套系统里，哪些东西和"做什么类型的项目"无关，哪些东西必须跟着项目类型变。

答案是两层分离：

- **结构流程**：阶段编排、执行闭环、状态与恢复、质量链、验收门禁。它与领域无关，适配新领域时按既有约定照常执行，不应改动。
- **领域知识**：phase 集合、各角色的具体规范、测试与验证命令、工程实践偏好。它从目标项目的特点推导，来源是对类似项目最佳实践的总结；而同一类项目往往存在多种都成立的最佳实践，所以最终取舍必须由人做出，不能让 AI 静默选定。

## 结构流程层：照常执行

以下内容与项目类型无关，属于结构流程。新领域接入时不修改它们，只把新领域注册进去：

- 主链路编排：`t-decision` 后按主要未知项分流到 `t-prd` / `t-tech-research`，在 `t-design` 前收敛；实现后经 accept 收口、`t-push` 本地 CI、`t-release` 发版。
- 阶段执行闭环：`t-super-run` 的目标级计划、主会话 dev/test、只读 accept；标准链路的 `phase -> slot -> item`。
- 状态与恢复：`.state.json` / `.pipeline.json` 状态机、证据失效重开、中断后同一命令从磁盘续跑。
- 质量链：`review --fix -> simplify -> push` 的固定顺序，以及"存在未修复正确性发现不得 push"。
- 门禁形态：accept 默认只读并输出可复核证据；按复杂度增减流程重量的拆分启发式；slot 上限触发用户确认。

判断一条规则属于结构还是领域，用一个替换测试：把项目从 Web 换成数据管道，这条规则还成立吗？

| 规则 | 归属 |
| --- | --- |
| 同一失败连续三次无进展转 `blocked` | 结构 |
| accept 只读并输出证据 | 结构 |
| 何时插入 test slot | 结构（规则本身） |
| backend runner 命令必须以 `uv run scripts/backend-test.py --` 开头 | 领域 |
| Playwright 用 `data-testid` 定位 | 领域 |
| test slot 里跑什么命令 | 领域 |

## t-super-run-all：结构流程已经解耦的证据

Git 历史里的 `t-super-run-all`（commit `f87bf32` 引入，`94f4549` 移除）是两层解耦最直接的证据。它是无人值守连跑入口：设计定稿后一次手工调用即授权整条链，把剩余全部 active phase 按序跑完。每个 phase 先执行 `t-super-run` 的阶段闭环，再执行质量链 `review --fix -> simplify -> push`，全部通过才进入下一个 phase。

它的构造方式说明结构层不依赖领域：

- phase 顺序被定义为 [task-phase-execution.md](/protocols/task-phase-execution.md) 默认顺序的"固定投影"，只取 `active_phases` 命中项。pipeline 本身不包含任何 phase 的内容知识。
- 每轮迭代先运行 `super-run-next.py` 从磁盘状态计算下一步 action，禁止凭内存推进；该脚本只读状态，不含领域判断。
- `.pipeline.json` 游标、`failures_without_progress` 失败计数、三次无进展转 `blocked`、停止条件，全部是领域无关规则。
- `t-prd-publish` 与 `t-release` 不在链内，仍由人手工触发。

它在一天后被移除，换回显式的 `t-super-run --phase` 逐段执行。值得注意的是移除清单：README、protocols、scripts 和几个 skill 的引用调整——`guides/` 与 `agents/` 一概未动。一个纯结构组件可以整体增删而不触碰任何领域内容，说明两层已经解耦。

这次增删同时说明：结构层自身也有取舍。无人值守连跑换速度，显式逐段执行换控制点，这是风险偏好，不是领域知识。这类取舍一次性决定、随仓库正常演进，不需要每个新领域重新裁决。

## 领域知识层：先总结候选，再由人选择

今天仓库里的领域知识分布在这些位置：

- [task-phase-execution.md](/protocols/task-phase-execution.md) 的 `supported_phases` 集合与各 phase 的启用条件。
- `agents/` 下每个领域的 `*-dev` / `*-test` / `*-accept` 角色规范。
- `guides/<domain>/` 里的开发模式、测试策略、验证命令和质量门禁。
- 具体验证命令与测试基建：`uv run scripts/backend-test.py`、`npm run test:run`、`flutter test`、Playwright / Patrol runner。
- Demo 形态：Web 与扩展用 Playwright E2E，Flutter 用 Android Patrol。
- `t-init` 的工程模板。

### 为什么必须由人选择

同一类项目的最佳实践不是只有一种。后端测试可以场景测试先行，也可以高价值单元测试优先；前端状态管理、组件测试与页面 E2E 的边界有多个都成立的组织方式；CLI 工具的"演示"可以是 golden-output 测试，也可以是录制式终端回放。这些选择没有客观最优，只有与团队、项目阶段和风险偏好匹配与否。

而 guides 一旦写入，后续每个 dev / test / accept 都会读取并执行它。适配时做一次偏好选择，成本最低；实现中途再换，等于推翻已经在轨道上的约束。把未经确认的最佳实践静默写进产物再继续推进，正是仓库规则明确禁止的行为：需要用户裁决的缺口必须暴露给用户。

所以泛化流程里的人工选择不是可选润色，而是领域层进入主链路的前置门禁。现有机制已经预留了位置：`t-decision` 分流、decision-continuity 契约、`AskUserQuestion` 确认，都是这个选择的记录通道。

## 泛化配方

适配一类新研发任务时，按以下顺序进行：

1. **确认结构层够用。** 新任务类型仍然是"需求 → 设计 → 实现 → 测试 → 验收 → 收口"的闭环吗？绝大多数研发任务是。结构层不动。
2. **从项目特点出发。** 读目标项目本身：语言、框架、构建与测试工具、已有脚本。验证命令必须来自目标项目真实脚本——这条既有规则就是领域层的锚点，防止总结出项目跑不起来的实践。
3. **总结类似项目的候选最佳实践。** 整理 2–4 套候选，每套内部一致：架构组织、测试策略、验证门禁必须成套出现，不能混搭出内部矛盾。每套写清代价，以及对门禁和证据形态的影响。
4. **由人做偏好选择。** 把候选连同取舍交给用户裁决，用既有 decision 机制记录（稳定 DEC ID 或 decision 文档）。未确认的假设不得写入 guides 或 agents。
5. **物化领域层。** 按选择落盘：新增 `guides/<domain>/`；把新 phase 注册进 `task-phase-execution.md`，含启用条件与默认顺序位置；新增对应 `*-dev` / `*-test` / `*-accept` agent；需要确定性重复执行的操作写进 `scripts/`；更新 `t-init` 模板和 README。
6. **验收形态跟着领域走，验收标准不变。** accept 仍然只读、基于证据。领域知识改变的是"证据长什么样"——什么命令、什么输出、什么演示形态；不改变"必须有可复核证据"。

结构流程层在这六步里没有一步需要修改。如果某个新领域真的逼你改结构层（例如无法定义可恢复的 item 边界），那说明遇到的是结构问题，应该按结构层的正常演进方式处理并在全仓库同步，而不是在领域层打补丁绕过去。

## 结语

T-Tools 的泛化能力不在于预置了多少领域，而在于结构流程与领域知识的边界是否干净。结构层提供轨道：可恢复、可验收、可门禁。领域层提供内容：由项目特点推导、从类似项目总结、经人类偏好选择后落盘。新增一类研发任务的成本，应当接近"总结候选实践 + 一次人的选择 + 物化一组 guide / agent / phase 注册"，而不是重新设计工作流。
