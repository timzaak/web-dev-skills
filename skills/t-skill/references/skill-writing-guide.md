# Skill 写作准则

融合 Anthropic skill-creator 与 Codex skill-creator 的写作实践。仓库硬性规则以根目录 AGENTS.md 为准；本文件只补充 AGENTS.md 之外的写作方法，冲突时以 AGENTS.md 为准。

## 触发：description 是第一道门

模型只凭 name 和 description 决定是否加载 skill，正文只有触发后才进上下文。因此：

- 一句"做什么" + 具体触发场景（用户实际会怎么表述）+ 与相邻 skill 的消歧边界，三样都要有。
- 欠触发比过触发更常见。描述要主动覆盖用户可能的间接说法——"用户提到 X、Y、Z 时使用，即使没有明说 W"，而不是等用户点名命令。
- 主动不等于贪多：catchall 式的能力清单会吸引无关请求；排除项只写防误路由所需，不枚举全部不适用场景。
- 简单一步任务模型自己就能完成，不依赖 skill；评估触发质量时不要拿这类查询当用例，要用带上下文、多步骤的真实请求。

## 渐进披露：三级加载

1. name + description — 恒在上下文，保持简短且可辨别
2. SKILL.md 正文 — 触发即加载，目标 500 行以内，接近就分层
3. references / scripts — 按需读取或执行，不占常驻上下文

分层规则：

- 正文保留共享目标、必要约束、核心流程和路由（何时读哪个文件）；分场景流程、schema、大段示例进 references。
- 超过 300 行的 reference 在开头加目录或可检索关键词。
- 同一内容只在一处维护，正文与 references 不互相复制。
- 简单自足的 skill 不需要 references 和路由层；不要为了"结构完整"而加层。

## 结构：按需最小化

```text
skills/<name>/
|-- SKILL.md        必需：frontmatter + 正文
`-- references/     仅当正文放不下且内容按场景分头使用
```

需要落到仓库其他位置的，按 AGENTS.md「规则归属」路由到 `agents/`、`protocols/`、`guides/`、`scripts/`，不在 skill 目录里复制一份。

不放入 skill 目录的东西：README、安装说明、changelog、正文的速查副本、没有调用方的占位文件。判断标准是"这个文件是否直接支撑 skill 的某次执行"；答案是否定的就不建。

## 写作原则

- **默认模型已具备能力。** 只写会改变其决策的内容：领域约束、非显然的上下文、已知的坑。删掉通用建议、教科书解释、推测性边界情况和没有实际约束力的说明。
- **自由度与风险匹配。** 多种做法都合理时，描述目标和判断标准，让模型自己选路；只有脆弱、必须一致或出错的代价很高的操作才固定步骤、命令或脚本。
- **保住用户的意图与边界。** skill 支持用户请求的任务，不扩大授权范围、不改无关配置。把某次失败或个人偏好写成普遍规则之前，先确认它真的普遍。
- **解释 why 优于堆砌 MUST。** 讲清原因，模型能举一反三；满篇 ALWAYS/NEVER 和僵硬结构是写作失控的黄旗，能解释清楚就替换成解释。
- **为一百万次使用而写，不为眼前三个样例过拟合。** 内容要在没见过的请求上也成立。
- **祈使句直接下指令。** 模板和示例给足何时必须照抄、何时仅供参考的边界。

## 示例模式

固定输出格式用模板并声明强制：

```markdown
## 报告结构
必须使用以下模板：
# [标题]
## 摘要
## 发现
## 建议
```

约定类规则用 Input/Output 对，比抽象描述更可靠：

```markdown
## Commit message 格式
输入：Added user authentication with JWT tokens
输出：feat(auth): implement JWT-based authentication
```

## 更新既有 skill

- 保留原 `name` 与目录名；入口形式变化会破坏用户习惯和下游引用。
- 动手前快照整个 skill 目录（测试对照与回滚都要用）。
- 修改前先搜索引用它的 skill、protocol、guide、agent、README 和 t-how 路由表；删除内容前先看它的调用方和存在原因。
- 只改用户要求或行为验证暴露的问题，不顺手重构无关段落。
